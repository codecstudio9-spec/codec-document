## International SEO (US English + 6 LATAM countries Spanish)

Architecture fixed 2026-07-29 — see `middleware.ts`, `src/app/data/hreflang-clusters.ts`, `src/app/components/seo-head.tsx`, `src/app/components/structured-data.tsx`, `scripts/generate-sitemap.mjs`.

- **URL structure**: distinct URLs per language/market (English slugs for US state/city pages, Spanish slugs for the 6 LATAM country pages) — this is intentional and Google-recommended; never migrate to `/us/` or `/latam/` path prefixes, it would force a redirect migration of ~190 already-indexed URLs for no SEO benefit.
- **Canonical/hreflang**: authoritative source is the HTTP `Link` response header set by `middleware.ts` (Vercel Edge Middleware, runs on every non-excluded route) — this is what non-JS-executing crawlers see. `SEOHead.tsx` reinforces the same values client-side once React mounts. **Never** hardcode a canonical/hreflang in `index.html` again — it's a single static shell served for ~190 different routes, so anything hardcoded there is correct for at most one of them.
- **hreflang is for genuine translations only**: `hreflang-clusters.ts` only registers pages that are the SAME content translated (currently empty — no such pair exists yet). A California lease-agreement page and a Colombia lease-agreement page are NOT hreflang counterparts — different documents, different local law, different markets. Don't add a "this is the LatAm version of that US page" entry; that tells Google they're interchangeable, which is false and can hurt both pages.
- **Content language must be deterministic per URL, not IP-based**: the app-wide `LanguageProvider` (`language-context.tsx`) still auto-detects language via IP/browser locale for the interactive app — but every SEO landing page template (`CountrySignatureLanding`, `DocTypeStateLanding`, `CityDocTypeLanding`, `CityLegalDocumentsLanding`, `StateLegalDocumentsLanding`, `StateDocumentLanding`) is wrapped in `FixedLanguageProvider` with a hardcoded default (`es` for LATAM country pages, `en` for everything US) so the crawlable snapshot never changes based on Googlebot's crawl IP. When adding a new landing page/template in this family, wrap it the same way — don't let it read the raw IP-detected `useLanguage()` for its primary content.
- **`StructuredData`**: pass `language` + `country` (with the country's real `lawBadgeEn`/`lawBadgeEs`, e.g. from `latam-signature-seo-content.ts`) on any non-US page — never let the US-specific ESIGN Act / "United States" JSON-LD claims render unchanged on a LatAm country page, that's a false legal claim in structured data, not just a copy mismatch.
- **Sitemap**: `public/sitemap.xml` is generated by `npm run generate:sitemap` (auto-runs as part of `npm run build` — see the `postbuild`-style chain in package.json's `build` script). Don't hand-edit it; add a new page to `routes.tsx` and it's picked up automatically, unless it needs excluding (see `EXCLUDE_PREFIXES`/`EXCLUDE_EXACT` in the script — keep in sync with `middleware.ts`'s `EXCLUDED` regex).
- **Thin-content checklist for any new document×state/country landing page**: ~600+ words of genuinely unique text (not just the state/country name swapped into a template), at least one real local-law citation (see `signature-jurisdictions.ts` / `doctype-state-seo-content.ts` for the pattern), unique meta title+description, its own FAQ (not just the generic site-wide one from `StructuredData`), and a real internal link to/from a hub page for that document type so the cluster reads as deliberate, not spun. Same topic-cluster principle as `feedback_seo_article_standard.md` (blog articles), applied to landing pages.
